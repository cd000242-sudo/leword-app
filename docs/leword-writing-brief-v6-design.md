# 오늘의 글감 v6 — 초보자 공통 기능 설계

상태: 설계·운영 지침 개정. 앱/사이트 구현·배포는 아직 하지 않음.
사용자 결정(2026-09-28): 특정 사이트나 작성자의 경험을 전제하지 않고 LEWORD 공통 기능부터 설계한다.
연결 지침: [실행용 편집 지침](prompts/leword-writing-brief-v6.md).

## 1. 제품이 해야 하는 일

첫 방문 사용자가 한 분야에서 글감 하나를 고르고, 추천 검색어와 확정 제목에 맞춰 출처 있는 글 한 편을 완성하도록 돕는다. 개인 실적 자료나 전문 경험이 없어도 시작할 수 있어야 한다.

공통 추천의 약속은 **‘검색 수요와 경쟁을 조사했고, 이 질문에 답할 재료를 준비했다’**이다. 사용자의 사이트 순위·수익을 검증했다고 약속하지 않는다. 장기 목표는 실제 유입·수익과 작성 노력 대비 기여의 개선이다. 내부 점수나 카드 수를 성공 지표로 대체하지 않는다.

## 2. 첫 사용 흐름

1. 글감은 입력 없이 탐색할 수 있다. 초기 공통 목록에서도 분야·적합 플랫폼·작성 상태를 표시한다.
2. `어디에 쓰시나요?`는 클릭 선택으로 제공한다. 플랫폼 미선택 상태는 탐색이며 모든 플랫폼에서 같은 효과를 낸다고 하지 않는다.
3. 분야를 고르면 그 분야의 가장 준비된 글감 1개와 다른 선택지 최대 2개를 먼저 보여준다. 이는 화면 우선 노출량이며 전체 서비스 생성 상한이 아니다. 준비된 패키지가 없으면 유효 저장본 또는 자료 보완 상태를 보여준다. 분야·플랫폼은 언제든 변경할 수 있다.
4. 글감을 열면 `주검색어 → 확정 제목 → 왜 쓰는가 → 어떤 답을 쓸 것인가 → 출처` 순으로 읽힌다.
5. `작성안 보기`에서 독자 상황과 이번 글에서 답할 범위를 먼저 확인한다. 근거 있는 선택지가 있다면 고른 범위의 검증된 작성안을 확정한 뒤 소제목별 본문 초안·값이 채워진 표·FAQ·마무리를 편집한다. 선택지가 없으면 공통 안내 초안으로 표시한다. `근거 보기`에서 주요 주장별 원문을 확인한다.
6. `작성안 복사`는 실제 작성 내용과 출처를 포함한다. 복사를 발행으로 기록하지 않는다.
7. 발행 후 URL을 선택 등록하면 그때부터 개인 중복·수정·성과 확인을 연결한다. URL 등록·분석 계정 연결은 필수 절차가 아니다.

초기 화면에 SEO 점수·CPC·SERP 같은 용어를 설명 없이 앞세우지 않는다. `실제로 묻는 질문 / 기존 글에서 빠진 답 / 글에 넣을 내용 / 아직 모르는 것`으로 설명하고 원자료는 펼쳐서 볼 수 있게 한다.

## 3. 플랫폼·수익화·초보자 적합성

| 게시 환경 | 검색 조사 | 수익화 표시 | 초보자 기본값 |
|---|---|---|---|
| 워드프레스·티스토리·Blogger 등 | 선택한 엔진의 외부 웹문서 영역 | 애드센스 사용 가능 여부·승인 상태는 별도 확인 | 공식 자료로 완성 가능한 문제 해결 글 |
| 네이버 블로그 | 네이버 블로그 및 실제 통합 검색 영역 | 애드포스트 등 해당 플랫폼 방식, 애드센스 예상수익 미표시 | 직접 경험을 가장하지 않는 안내·비교 글 |
| 아직 미정 | 카드마다 조사한 엔진·영역을 표시 | 수익화 미정 | 분야와 플랫폼을 고르는 탐색 자료 |

신규 사이트의 당일 색인을 가정하지 않는다. 경험·구매·방문·실험 없이는 유용한 답을 제공할 수 없는 글감은 기본 추천에서 제외한다. 의료 진단·개인별 법률/보험 결론 같은 전문 판단을 초보자의 자료 요약으로 대체하지 않는다. 대상 확인·공식 절차 안내처럼 검증 가능한 범위는 별도로 검토할 수 있다.

검색 유입과 광고 게재 가능 상태는 독립적이다. 미승인 사이트에도 작성 재료를 제공하되 ‘이 글을 올리면 바로 수익 발생’이라는 표시를 하지 않는다.

## 4. 공개 글감과 개인 작성안 분리

- **공통 자료:** 공개 출처, 확인한 질문, 검색 수요 관측, 경쟁 문서 비교, 공통 설명·조건표, 조사 시각과 유효기간.
- **사용자 선택:** 플랫폼, 분야, 독자 상황·세부 질문, 작성 상태. 선택에 따라 제목과 답변 범위를 다시 맞춘다.
- **개인 자료:** 연결한 사이트·발행 이력·분석 지표·미발행 원고·수익. 별도 권한과 저장소로 관리하고 공통 JSON으로 공개하지 않는다.

모든 사용자에게 같은 제목·원고 복사를 성공 방식으로 제시하지 않는다. 공통 자료를 바탕으로 실제로 다른 독자 질문을 해결할 수 있을 때만 선택지를 제공한다. 선택지가 다른 사건·지역·대상으로 바뀌면 근거·수요·경쟁도 해당 범위에서 다시 확인한다. 단어 바꾸기·무작위 문체 변경·지역명 치환으로 ‘나만의 글’을 만들었다고 하지 않는다.

동일 글감을 여러 사용자가 받을 수 있음을 설명하고 독점 노출을 약속하지 않는다. 시간이 지나 경쟁과 정보가 바뀌면 재심사한다. LEWORD 안의 복사 횟수와 외부 발행 수를 혼동하지 않는다.

## 5. 발굴·판정 단계

`실제 질문·공식 변경·뉴스 본문 수집 → 의미 중복 제거 → 주검색어 선정 → 수요 관측 → 해당 플랫폼 경쟁 조사 → 공식 답변 조사 → 작성 패키지 구성 → 검수 → 공개`

개인 사이트가 연결됐을 때만 기존 글 수정 기회와 개인 중복 검사를 추가한다. AI는 자료를 정리하고 문장을 만드는 역할이다. 측정값·출처·날짜·관문 통과 여부의 필수 조건은 결정적인 검증 로직으로 확인한다.

### 반드시 나눌 상태

| 상태 | 조건 | 첫 화면 취급 |
|---|---|---|
| 작성 추천 | 실제 수요 근거·경쟁의 빈틈·충분한 답변·초보자 작성 가능·플랫폼 적합 확인 | 기본 추천 카드 |
| 검증 실험 | 신규 수요가 가설, 나머지 작성 조건은 충족 | 별도 선택, 기본 추천 수에 미포함 |
| 자료 보완 | 제목의 핵심 답·수요·경쟁 등에 미확인 존재 | 별도 목록, 바로 쓰기 강조 금지 |
| 보류 | 수요 근거 없음·가치 부족·기간 종료·필수 경험 없음 등 | 기본 목록에서 제외, 사유 보관 |
| 기존 글 수정 | 연결한 개인 글에 구체적인 보완 기회 있음 | 개인 화면에 수정안 제공 |

`원문 사실 검토 완료`는 `작성 추천`과 다르다. 현행 editorial.status=supported를 자동 승격하지 않는다. 공통 추천의 개인 중복·개인 수익 미확인은 숨기지 않되, 개인 데이터 미연결만으로 모든 공통 추천을 차단하지 않는다.

기존 앱의 데이터 기반 SSS/SS/S/A/B 등급을 이 상태로 재정의하지 않는다. 신규 상태는 글 작성 준비 여부다. CPC 추정이 필요하면 기존 단일 CPC 소스를 사용하며 별도 임의 테이블을 만들지 않는다.

## 6. 글감 한 건의 화면 구성

카드 전면:

> **[확정 제목]**
> 주검색어: [실제 조사한 표현] · 적합 플랫폼: [플랫폼]
> 이런 독자가 읽습니다: [구체적인 상황과 질문]
> 지금 쓸 이유: [확인한 수요·변화와 제공할 가치]
> 준비된 내용: [답변·조건표·절차 등의 실제 구성]
> 확인 기준: [시각] · [공통 추천 / 개인 맞춤]
> [작성안 보기] [추천 근거]

대괄호는 화면 설계의 자리 표시다. 실제 결과에서 빈 칸·가짜 데이터로 사용하지 않는다.

작성안 상세는 다음 순서다.

1. 확정 제목 하나와 주검색어. 보조 표현은 같은 질문 안에서만 묶고 실측/제안 구분.
2. 핵심 답을 먼저 주는 도입부 2~4문장.
3. 필요한 소제목마다 완결된 초안 문단, 조건·예외·행동, 근거 연결.
4. 값을 채운 대상 판단표·비교표·체크리스트 중 유용한 도구. 모든 글에 동일한 표를 억지로 넣지 않음.
5. 본문에서 다루지 못한 실제 질문과 FAQ, 공식 경로, 마무리.
6. 사용자에게 남은 일: 문체 정리, 직접 경험을 넣고 싶으면 실제 경험 추가, 자신의 추가 문장 확인, 발행 직전 지목된 변경 가능 정보 확인. 마지막 항목은 확인할 URL·항목·기준일을 제공. LEWORD가 공개 전 핵심 주장과 출처를 검수하며 핵심 재조사가 남으면 작성 추천에서 제외. 개인 시간 적합성은 선택 입력이 있을 때만 별도 판단.
7. 주요 주장별 출처와 확인 날짜. 원문 긴 복제를 피하고 사실과 조건을 보존.

추천 근거 상세는 수요 규모/근거, 경쟁 문서 URL과 빈틈, 검토 범위, 시기, 작업 부담, 수익 근거 상태를 보여준다. 초보자에게 광고 단가가 높다는 말로 선택을 유도하지 않는다.

## 7. 데이터 계약: 후속 구현의 최소 요구

현행 editorial v2는 보존하고 별도 `writingPackage.version=1`을 추가하는 방식부터 검토한다. 구형 저장본을 새로운 검증을 통과한 것으로 취급하지 않는다.

| 필드 그룹 | 필수 의미 |
|---|---|
| identity | 안정적인 후보 ID, 사건/주제 ID, 질문 ID, 분야, 언어·지역, 버전 |
| audience | 독자 상황, 질문, 선택한 범위, 플랫폼·검색엔진·검색 영역 |
| demandEvidence | 조회 검색어·출처·측정 시각·대상 기간·값/범위/미확인·증거 유형 |
| competitionEvidence | 실제 화면/API 구분, 조회어·시각·표본 범위, URL별 답변 충족/누락 |
| sources | 문서 URL·기관·문서/시행 날짜·조회 시각·적용 범위·열람 상태 |
| claims | 주요 주장 ID, 답변, 조건·예외, 해당 source ID·근거 위치 |
| writingPackage | 제목, 도입부, 소제목별 초안·claim IDs, 채워진 표/체크리스트, FAQ, 마무리 |
| assessment | 관문별 판정과 evidence IDs, 추천 상태, 부족한 항목, 초보자 작업 요구 |
| freshness | 생성·조사·저장본 시각, 시간 민감 항목별 만료/재확인 조건, 사건 유효기간 |
| provenance | 생성·검수 방식, 미완료 단계, site/app 출처, 저장본 여부 |
| monetization | 수익화 방식, 근거 상태, 관측 기간·PV·수입·통화·분모, 가정은 별도 |
| personalOverlay | 소유자 권한, 개인 사이트·발행 URL·개인 중복·성과. 공통 공개 스키마에서 제외 |

관문은 필드 존재만으로 통과시키지 않는다. 제목의 약속과 핵심 주장, 주장과 출처의 내용 일치까지 검토해야 한다. 사용자 화면에서 자유 서술 점수 하나만으로 추천 상태를 결정하지 않는다.

## 8. 현재 코드에서 바꿔야 할 부분

- `src/utils/topic-briefs.ts`, `topic-brief-prompt.ts`: 기사 중심 초안에서 주검색어·독자 질문·플랫폼별 작성 패키지로 확장.
- `src/main/topic-brief-pipeline.ts`: 현재 원문 보강은 공유 뉴스 리더를 사용하며 네이버 허용 범위·문서 수·시간 제한이 있다. 지침에 ‘공식 자료 확인’을 넣는 것만으로 기관 원문을 읽을 수 없다. 공식 출처 검색·본문 추출 단계를 별도로 설계하고 SSRF·리다이렉트·용량·시간 제한을 유지한다. 기존 허용 목록을 무조건 해제하지 않는다.
- `src/utils/topic-brief-evidence.ts`: 제목-답변-출처 검사에 조건표·초안 완성도·수요/경쟁 증거 검증 추가. 현행 근거 검토와 추천 판정의 차이를 유지.
- `scripts/topic-briefs.js`, `src/main/handlers/topic-briefs-local.ts`: 같은 공통 파이프라인과 판정 계약 사용. 서버/앱 생성 결과의 품질 조건을 통일.
- `src/main/board-cache.ts`: 새 공개 필드만 whitelist에 추가. 개인 데이터는 별도 전달. 구형 보드 안전한 표시와 원래 시각 보존.
- 앱 `ui/keyword-master.html`과 사이트 `TopicBriefsBoard`: 같은 상태와 작성 패키지를 표현. 앱은 기존 인라인 스타일 규칙 유지. 사이트만 좋아지고 앱이 뒤처지지 않게 동시 검증.

## 9. 할당량·실패·캐시

공통 사실·검색 관측은 유효기간 내 재사용한다. 페이지를 열거나 분야 필터를 바꾸는 것만으로 모델을 재실행하지 않는다. 사용자별 모든 조회에 원문 수집·AI 생성을 반복하지 않는다.

공통 배치는 분야·플랫폼·검색엔진 조합을 조사 단위로 삼고 실행 전에 전체 예산과 대상 단위를 정한다. 단위당 후보 15개·상세 조사 5개·완성 패키지 최대 3개를 작업량 기본값으로 삼되 전체 예산에 맞춰 배분한다. 사용자 화면의 우선 노출 최대 3개와 생성 예산은 별개다. 이 수치는 SEO 합격 기준이나 모든 분야의 일일 생성 보장이 아니다.

`후보·관측 수집 → 출처·사실표 → 작성 패키지 → 검수·공개` 단계별 결과·입력 버전·완료 상태·조사 시각을 저장한다. 할당량 실패 후에는 유효한 완료 단계를 재사용하고 미완료·만료 단계부터 재개한다. 중간 산출물은 검수된 패키지와 분리한다. 개인 분석 연결·최초 전체 발행 목록 수집은 공통 배치와 별도 작업으로 둔다.

새 패키지는 검수까지 완료한 후 원자적으로 교체한다. 실패·취소·빈 결과는 직전 정상 저장본을 지우지 않는다. site/app 저장본을 가져오더라도 작성 근거와 현재 경쟁 관측을 구분한다. 유효기간이 지난 경쟁·마감 정보는 새 timestamp를 붙여 살리지 않는다.

앱 폴백은 기존처럼 같은 PC의 앱 저장본을 읽는 범위다. 이를 전체 사용자에 공개하는 기능으로 확대하려면 별도의 공개 투영·게시 주체·권한 설계가 필요하다. 개인 작성안을 다른 사용자에게 보충 자료로 공유하지 않는다.

모든 후보가 미달이면 0개와 구체적 원인을 보여준다. 같은 분야의 유효한 저장본 또는 준비된 기존 글 수정안을 안내할 수 있으나 미검증 후보를 대신 추천하지 않는다.

## 10. 설계의 반례 검사

아래는 구현 전 수용 기준이다. 실제 코드 테스트가 통과했다는 뜻이 아니다.

| 입력 상황 | 반드시 나와야 하는 결과 |
|---|---|
| 신규 사용자, URL·성과·경험 없음 | 공통 탐색/추천 사용 가능, 개인 중복·수익은 미확인 |
| 네이버 블로그 선택 | 해당 검색 영역 검토, 애드센스 예상수익 표시 없음 |

| 뉴스 대상 인원만 많고 검색·질문 증거 없음 | 검증 실험 또는 보류, 수요 실측으로 승격 금지 |

| 광고 입찰가는 높지만 수요·수익 자료 없음 | 돈 되는 글로 확정 금지, 예상수익 미확인 |
| 발행 기회가 오늘 종료, 검색 반영 기간 모름 | 당일 선점 확정 금지, 후속 질문이 있으면 새로 검증 |
| 기존 글에 같은 답이 이미 있음(연결 사용자) | 새 글보다 기존 글 수정 검토 |
| 같은 후보를 여러 사용자가 선택 | 독점 보장 없음, 사실 있는 질문별 구성만 제공 |
| 사용자 질문 범위를 다른 지역으로 변경 | 지역 자료·경쟁 재검증 전 제목만 치환해 완료 처리 금지 |
| 생성 CLI 모두 실패, 유효 앱 저장본 존재 | 원래 출처·시각으로 복구, 조회에 AI 재호출 없음 |

| 개인 작성 시간 미입력 | 구체적인 남은 작업 제공, 시간 적합성 확정이나 추천 차단 없음 |
| 해당 분야의 새 패키지 없음 | 유효 저장본/자료 보완 상태, 수량을 채우기 위한 미검증 생성 없음 |

## 11. 검증 순서와 완료 기준

1. **실자료 패키지 검증:** 서로 다른 분야에서 실제 후보를 조사한다. 추천할 수 없는 후보도 보존한다. 핵심 사실·제목의 약속·표·출처가 모두 연결된 패키지만 다음 단계로 넘긴다. 수량 충족을 위해 기준을 낮추지 않는다.
2. **초보자 사용성 검증:** 서로 다른 초보자 3~5명이 작성안만 보고 초안을 만든다. 플랫폼을 나눠 보고, 어디에서 추가 검색이 필요했는지·용어 때문에 멈췄는지·얼마나 시간이 들었는지 기록한다. 필요한 핵심 정보가 빠졌다면 지침과 파이프라인을 수정한다. 이 표본으로 수익 성공률을 주장하지 않는다.
3. **앱·사이트 수용 검사:** 위 반례를 실행 테스트로 만들고 실제 저장본·API 실패·구형 보드·플랫폼 전환·복사 결과를 함께 확인한다. 개인 정보 분리와 GET AI 미호출은 필수다.
4. **동의 기반 성과 파일럿:** 발행 URL과 가능 범위의 7·14·28일 유입·수입·작업 시간을 수집한다. 무유입·미색인·중도 포기 사례도 포함한다. 사이트 규모·플랫폼·글의 경과 시간을 구분하고 선택 편향을 밝힌다.

초기 출시 완료 조건은 ‘초보자가 완성 가능한 정확한 패키지’와 ‘실측·추정 구분’이다. 수익 개선은 후속 실측으로 평가한다. 수익이 확인되기 전에 자체적으로 95점·100점 제품이라고 홍보하지 않는다.

## 12. 사용자에게 도움받을 부분

대표 사용자의 개인 분야나 수익 자료를 모든 사람의 기본값으로 삼지 않는다. 사용자가 도와줄 가장 가치 있는 부분은 실제 초보자 2~3명에게 시제품을 사용하게 하고, **이 내용만 보고 쓸 수 있었는지, 어디에서 막혔는지**를 함께 관찰하는 일이다.

그 전에 개발 측에서 실자료 패키지와 검수 결과를 먼저 준비한다. 사용자가 좋은 글감의 답을 대신 조사하거나 설계 공백을 메우게 하지 않는다.
