# 홈판 신호 — 작성 판단과 제작 연결 개선 계획

작성일: 2026-09-17. 상태: APP·SITE 구현 및 로컬 통합 검증 후 사용자 요청으로 v2.49.139 출시 진행. 실제 자료 20건의 내용 품질 평가는 후속으로 남아 있으며, 미검토 결과를 준비 완료로 표시하지 않는다. 구현·검증 기록은 문서 끝에 정리한다.

## 1. 목표와 완료 상태

홈판 신호에서 소재 하나를 열면 사용자가 다음을 이해하고 작성 여부를 결정할 수 있어야 한다.

1. 누구에게 무슨 일이 생겼는가.
2. 지금 다룰 이유와 예상 독자의 궁금증은 무엇인가.
3. 어떤 관점으로 쓰며, 수집한 기사들과 어떻게 달라지는가.
4. 본문에서 답할 질문과 이를 뒷받침하는 구체적 사실은 무엇인가.
5. 무엇이 확인됐고 무엇이 부족한가.
6. 선택한 관점·제목·첫 카드·이미지가 원고에 어떻게 반영되는가.

검색량과 기사 수는 관측값, 독자 관심과 추천 관점은 편집 제안으로 구분한다. 홈판 노출 확률이나 실측하지 않은 독자 반응을 만들지 않는다.

## 2. 확인한 문제와 기준 사례

2026-09-17 16:06 KST 로컬 공개본은 스토리 12개, NOW 1개였다. 검토 시점의 저장 결과이며 기사 내용 자체를 외부 확인한 기록은 아니다.

| 확인된 결과 | 원인 | 수정 후 요구 |
|---|---|---|
| NOW 소재의 첫 카드가 `남산 명동` | 기준어에 새로 관측한 첫 토큰을 연결 | 대상과 사건의 관계가 보이는 표현. 준비가 안 됐으면 추천 문구로 표시하지 않음 |
| `박은지 미국서`, `파티 발표` | 상황을 설명하는 내용보다 토큰의 발견 순서 우선 | 장소·일반 동사만으로 완성 카드 처리 금지 |
| 다른 각도 `대법원`, 풀 이야기 8개 | 제목 토큰과 숫자·인용·사건어의 개수 | 질문·답·출처가 연결된 작성 관점과 본문 재료 |
| 카테고리만 알면 1초 이해 통과 | 의미 판단을 사전 매칭으로 대체 | 관측과 편집 검토의 결과를 각각 표시 |
| 앱은 6열 표, 사이트 공개본은 상세에서 앱 요구 | 앱 IPC 2개, 공개 데이터는 목록 전용 | 양쪽에서 같은 작성안 열람, 공개본 상세도 열람 가능 |
| 카드 선택·편집과 원고 입력 불일치 | A/B/C만 localStorage, 문구·이미지는 화면 메모리 | 선택 전체를 저장하고 원고 생성에 명시적으로 전달 |

## 3. 우선 결정

- 기존 수집기·실측 시계열·구독 에이전트 실행기를 재사용한다.
- 목록·상세 열람은 저장된 결과만 읽는다. 화면을 볼 때마다 AI를 부르지 않는다.
- 최초 작성안 생성은 사용자 동작으로 실행한다. 개별 생성과 `후보 최대 3건 작성안 만들기`를 제공하며, 적합한 후보가 적으면 수를 억지로 채우지 않는다.
- 생성 전에는 출처를 명시한 기사 제목/요약과 `작성안 준비 전`을 보여준다. 이를 자체 작성한 제목이나 검증된 새 사건으로 포장하지 않는다.
- 생성된 작성안이 없는 최초 실행에서도 소재 탐색과 근거 열람은 가능하다. 다음 이력이 쌓여야 하는 시계열 비교만 미측정으로 둔다.
- 기사 제목만 확보된 후보를 장문 원고 작성 준비 완료로 표시하지 않는다. 확보한 요약 또는 본문이 충분한지를 사실별로 확인한다.
- 전역 등급·CPC·다른 키워드 기능은 수정 범위에 넣지 않는다. 변경은 homefeed 계약과 연결부 중심으로 한다.

## 4. 단계별 구현

### 단계 0 — 계약과 실패 사례 고정

후속 변경이 공통으로 사용할 데이터 계약과 회귀 사례부터 만든다.

- 기존 실제 스냅샷·공개본에서 단어 조각 카드, 동일 사건 중복, 오분류 사례를 고정한다.
- 이전 `story.id`는 델타에 따라 바뀔 수 있으므로 작업의 대상과 근거 버전을 별도로 식별한다.
- 새 데이터는 `issueKey + evidenceRevision + briefRevision + selectionRevision`으로 연결한다.
- IPC·웹 브리지·공개 파일에 필요한 읽기 전용 응답과 편집 응답을 구분한다.
- 기존 브리지 파일의 미커밋 변경을 먼저 확인하고 homefeed 연결 외 변경을 덮어쓰지 않는다.

완료 기준: 변경 후에도 스냅샷, 기존 원고, 이미지, 발행 기록이 보존되는 읽기/쓰기 계약을 정한다.

### 단계 1 — 작성에 필요한 근거 확보

뉴스 제목 중심 입력에 검색 요약과 필요한 기사 내용을 보완한다.

- 홈판의 뉴스 어댑터에서 API 응답의 `description`, `originallink`, 발표 시각, 수집 시각을 보존한다. 공용 `parseNewsHeadlines`의 기존 소비자 동작은 유지한다.
- 작성안 생성 대상으로 선택한 이슈에 한해 최대 3개의 서로 다른 기사에서 읽을 수 있는 내용을 가져온다. 동일 기사 재전송과 같은 문장 반복은 독립 사실 수로 세지 않는다.
- 지원하는 뉴스 페이지부터 시작하는 작은 기사 리더를 홈판에 둔다. 타 저장소의 대형 `sourceAssembler.ts`를 직접 import하지 않는다.
- `issue-brief-extractor.ts`의 문장 정제·잘린 문장 제외·출처 연결 원칙을 재사용하되, 검색 결과 요약을 기사 전체 본문으로 취급하지 않는다.
- 근거마다 `sourceId`, 정규화한 주소, 제목, 매체, 시각, 본문/요약/제목 구분, 확인 가능한 문장, 내용 해시를 남긴다.
- 실패·차단·빈 본문은 그 상태대로 저장한다. 제목만 남으면 확인 범위를 낮추고 추가 확인 항목을 제시한다.
- 제목 변경, 같은 URL의 기사 수정, 부정문, 인용 화자, 서로 충돌하는 보도를 보존한다.
- 기사 취득은 정해진 시간·크기·개수 한도 안에서 실행하고 URL/리디렉션을 검증한다. 이미 받는 OG 정보와 중복 요청을 줄인다.
- 이번 회차에 같은 기사/같은 사건을 가리키는 후보는 중복 작성안을 만들지 않도록 묶는다. 동일 인물의 다른 사건은 근거 없이 합치지 않는다.

완료 기준: 작성안의 사실 문장마다 실제 근거 구절을 찾아갈 수 있다. 수집 실패가 전체 이슈 목록을 지우지 않는다.

### 단계 2 — 근거에 연결된 작성안 생성

새 `EditorialBrief`를 중심 결과물로 추가한다. 기존 긴장·재미 태그는 보조 정보로 둔다.

| 작성안 항목 | 내용 |
|---|---|
| 사건 요약 | 주체·행동·대상·현재 상황을 담은 문장과 근거 ID |
| 지금 다룰 이유 | 확인된 변화, 프로그램이 새로 발견한 보도, 시계열 관측을 구분 |
| 예상 독자와 궁금증 | 어떤 사람이 무엇을 궁금해할지에 대한 편집 제안 |
| 추천 관점 1개 | 글이 답할 중심 질문과 수집 기사 대비 차별점 |
| 대안 관점 최대 2개 | 실제 근거가 뒷받침하는 경우에만 제공 |
| 본문 재료 | 핵심 질문 최대 3개, 답할 사실, 근거 ID, 부족한 부분 |
| 제목·첫 카드 초안 | 선택 관점의 내용과 일치하는 자연스러운 표현 |
| 확인 범위 | 제목/요약/본문, 상충 보도, 확인이 필요한 사실 |

- 추천 관점과 각 사실을 근거에 연결한다. 참조 ID가 존재한다는 사실만으로 내용까지 검증됐다고 처리하지 않는다.
- 생성 1회 → 근거와 의미 검토 1회 → 필요한 경우 수정 1회로 횟수를 제한한다. 실패하면 마지막 정상 결과를 유지하고 실패 이유를 보여준다.
- 자동 검사는 응답 구조, 출처 존재, 인용·수량·시각, 모순 상태, 빈 필드, 잘린 문장을 확인한다. 의미 검토는 주체·행동·부정·인용의 일치와 추천 관점의 근거를 확인한다.
- 한 사실을 숫자·사건어·인용으로 반복해서 본문 재료 수를 부풀리지 않는다. 재료가 1개면 1개만 보여준다.
- 이전에 본 적 없는 표현을 곧바로 `새 사실`로 부르지 않는다. 보도 시점과 사건 시점을 구분하고 확인 불가하면 `이번에 새로 확인한 내용`으로 제한한다.
- “기존 글과 다름”의 비교 범위는 실제 수집한 기사 표본으로 한정한다.
- 관측 순위와 추천 관점을 모두 읽을 수 있게 하되, 근거가 충분한 작성안을 앞에 두는 정렬을 추가한다.

완료 기준: `남산 명동` 같은 조각은 완성된 추천 카드가 될 수 없다. 자연스러운 문장이어도 근거가 부족하면 작성 준비 완료가 될 수 없다.

### 단계 3 — 판정과 화면을 작성안 중심으로 전환

- 목록의 첫 정보: 사건 한 문장 → 추천 관점 → 독자 질문 → 작성 준비 상태 → 핵심 근거.
- 실시간 순위·증가량·제목 유사도는 근거 펼치기로 이동한다. `같은 제목 포화`가 뉴스 표본 유사도임을 분명히 표시한다.
- 상세의 기본 화면을 `작성안`으로 한다. `관측 근거`, `제목·첫 카드`, `원고`로 이동한다.
- `1초 이해`, `멈추게 함` 같은 검증되지 않은 성과 단정을 제거한다. 실제 수행한 검사와 편집 검토 결과만 표시한다.
- 기존 WINDOW/STATUS는 시점·규칙 판정으로 보존하되, 사용자에게 `지금 작성 추천`으로 보여주려면 현재 근거에 맞는 작성안 검토와 준비 상태도 충족해야 한다.
- 준비 상태는 `준비 전 / 추가 확인 / 작성안 준비됨 / 근거 변경 / 생성 실패`로 설명한다. 내부 수집·생성 상태와 노출 성과를 섞지 않는다.
- 쓸 만한 근거가 없는 후보는 기본 목록에서 접고, 사유와 함께 다시 볼 수 있게 한다.
- 미분류는 분류 미확인일 뿐, 사람들이 이해하지 못한다는 판정으로 사용하지 않는다.
- 앱은 인라인 스타일을 유지하며 상세 열람과 작성 동작을 추가한다. 사이트는 기존 컴포넌트 구조 안에서 같은 응답 의미를 사용한다.

완료 기준: 앱과 사이트 모두 첫 화면에서 소재의 내용과 추천 이유를 읽을 수 있다. 지표를 해석해야만 글감을 알 수 있는 구조가 해소된다.

### 단계 4 — 선택 저장부터 원고까지 연결

- 저장할 선택: 작성안 버전, 선택 관점 ID, 제목 ID/편집 문구, 카드 종류, 카드 두 줄, 이미지 참조, 선택 버전.
- 이미지와 근거는 배열 순번 대신 안정적인 자산/출처 ID로 참조한다. 기사 순서 변경으로 다른 이미지가 선택되지 않아야 한다.
- localStorage의 A/B/C는 기존 화면 선호로만 읽고, 예전 카드 문구·이미지를 선택했다고 추정하지 않는다.
- `이 관점으로 쓰기` 또는 `이 카드 사용`에서 서비스에 선택을 저장한다. 저장 성공 후 다음 단계로 이동한다.
- 앱 IPC와 사이트 브리지가 같은 선택 서비스를 호출한다. 입력 길이·관점/제목/이미지 소속·버전을 양쪽에서 동일하게 검사한다.
- 제목·카드가 선택한 관점과 맞는지 검사한다. `pair.titleId`와 실제 고른 제목의 일치도 확인한다.
- 원고 재료는 선택한 관점, 저장된 카드, 구체적 사실, 근거 구절에서 만든다. 이전의 제목 목록만으로 장문을 채우는 경로는 준비 부족 상태로 돌린다.
- 초반 내용이 카드의 질문에 실제로 답하는지 검토한다. 단어가 등장하는지만 확인하지 않는다.
- 기사에 없는 수량·경험·인용을 문체 규칙 때문에 만들어내지 않도록 원고 지침과 검사 기준을 함께 바꾼다.
- 근거 변경 후에는 기존 제목/카드/원고를 이력으로 보존한다. 최신 결과와 자동 혼용하지 않고 갱신 또는 선택 재검토 동작을 제공한다.

완료 기준: 카드 문구와 이미지를 고르고 화면을 닫거나 앱을 재시작해도 선택이 복원된다. 원고가 해당 선택 버전에 연결된다.

### 단계 5 — 앱 없이도 읽히는 사이트 상세

- 공개 목록과 같은 버전의 공개 상세를 함께 만든다. 첫 구현은 후보 수가 작으므로 같은 공개 파일 안에 읽기 전용 상세를 포함해 목록/상세 버전 불일치를 피한다.
- 공개 상세에는 공통 소재 요약, 근거 링크, 제한된 근거 설명, 공개 대상으로 지정된 작성안을 포함한다.
